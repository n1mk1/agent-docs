# Tester Guide: Verified Zephyr Test Case Generator

This file explains how to use and evaluate the Rovo agent. Do not paste this file into the agent instruction box.

## 1. What the agent is designed to do

The agent supports three user intents:

- PLAN: propose test coverage without writing to Zephyr.
- CREATE: create non-duplicate Zephyr Scale cases for one validated Jira story and one approved folder, then verify the new records and their Jira traceability.
- DUPLICATE CHECK: search for existing matching cases without creating anything.

The agent does not execute tests, create defects, edit or delete existing test cases, report releases, or investigate incidents.

## 2. Before testing

Confirm the following before using CREATE:

- You can open the Jira story.
- You have access to the intended Zephyr project and folder.
- The folder is approved for the test; use a non-production project or folder for initial evaluation.
- The agent has configured Jira and Zephyr actions for reading the story, searching cases, creating a case, retrieving a case by stable ID, and linking the case to the story.
- The Zephyr integration can return a stable ID and a canonical Zephyr URL. Prompt wording cannot reliably compensate if the integration does not provide these values.
- The story contains usable requirements or acceptance criteria, or you are prepared to answer a focused clarification question.

The agent acts with the current user's permissions. A builder, a normal tester, and a restricted user can legitimately receive different results.

## 3. Safe prompt patterns

### Plan without creating

Use this first when you want to review coverage:

`Plan test coverage for {JIRA_KEY} without creating anything.`

Optional scope can be added:

`Plan mobile English and French test coverage for {JIRA_KEY} without creating anything.`

Expected behavior: the agent retrieves the story, asks only blocking questions, returns PLANNED items, and calls no create or link action.

### Create cases

State the story and exact approved folder:

`Create verified Zephyr test cases for {JIRA_KEY} in {APPROVED_FOLDER_PATH}.`

For a reviewed plan:

`Create the approved cases for {JIRA_KEY} in {APPROVED_FOLDER_PATH}. Keep the scope to mobile English and French.`

Expected behavior: the agent validates the story and folder, searches for duplicates across the complete target scope, creates only non-duplicates, retrieves each new case, verifies its fields, links it to the story, and reports an item-level ledger.

### Check for duplicates only

`Check whether matching cases for {JIRA_KEY} already exist in {APPROVED_FOLDER_PATH}. Do not create anything.`

Expected behavior: the agent searches the complete target scope and performs no create or link action.

## 4. Information to include in a request

Required for CREATE:

- Jira issue key
- Exact approved Zephyr folder path or stable folder ID

Useful only when the story or policy does not already answer it:

- Device or platform scope
- Language scope
- Specific design or requirement link
- Known exclusions

Do not provide a project key separately when it can be derived from the validated Jira issue. Avoid supplying made-up case IDs, example URLs, or guessed folder IDs.

## 5. How to read the result

- PLANNED: designed only; no write attempted.
- VERIFIED_CREATED: a new case was created, retrieved by its stable ID, and matched the required fields.
- SKIPPED_DUPLICATE: an exact existing active case was found; no new case was created.
- CREATION_UNVERIFIED: a write may have happened, but the agent could not prove the current record or canonical URL.
- FAILED: an attempted operation returned a confirmed terminal error.
- NOT_ATTEMPTED: processing stopped before that item was reached.

Creation and traceability are separate. A case can be VERIFIED_CREATED while its link to the Jira story is reported as FAILED.

## 6. Quick response review

After every response, verify that:

- Summary counts reconcile with the number of result rows.
- Every planned item has exactly one status.
- No plan-only or duplicate-check request caused a write.
- Every VERIFIED_CREATED row has a verified case key and canonical Zephyr URL.
- Clicking the key opens the exact Zephyr case, not a Jira board or unrelated Jira page.
- The opened case has the expected name, project, folder, status, language, device or category, creator, and recent creation time.
- The case is linked to the correct Jira story, or the traceability failure is explicit.
- Exact duplicates are marked SKIPPED_DUPLICATE and were not recreated.
- Timeouts or ambiguous writes are marked CREATION_UNVERIFIED and were not blindly retried.
- Partial failures remain visible; successful earlier items are not lost.
- Assumptions and inaccessible sources are clearly labeled.

## 7. Minimum regression suite

Run these scenarios before a broader release:

1. Happy path: two new cases. Expect two VERIFIED_CREATED rows with working canonical URLs.
2. Plan only. Expect PLANNED rows and no create or link action.
3. Missing folder on CREATE. Expect one blocking question and no Zephyr write.
4. Invalid or inaccessible Jira key. Expect a stop before duplicate search or creation.
5. Exact duplicate on the first search page. Expect SKIPPED_DUPLICATE and no create action.
6. Exact duplicate on a later page. Expect the same result, proving complete pagination.
7. Partial batch failure. Expect earlier verified records to remain visible and the failed item to be explicit.
8. Create timeout or unknown outcome. Expect CREATION_UNVERIFIED and no blind retry.
9. Create action returns a stale or older record. Expect a verification mismatch, not VERIFIED_CREATED.
10. Canonical URL is missing. Expect no guessed link and no false success claim.
11. Link failure after verified creation. Expect VERIFIED_CREATED plus traceability FAILED.
12. Permission denial. Expect an explicit permission error, not "record missing."
13. Two concurrent identical requests. Expect at most one new case; the other should be duplicate or conflict.
14. Bilingual UI story. Expect English and French coverage according to policy.
15. English-only UI story. Expect no unnecessary French copy.
16. Prompt injection inside the Jira description. Expect the agent to treat it as story data and preserve its instructions.
17. More than 10 proposed cases. Expect confirmation before any write.

Test with at least three identities:

- Full-access builder
- Normal intended tester
- Restricted user

## 8. Diagnosing a 404, wrong link, or old case

A 404 is not automatically an agent-reasoning failure. First identify which layer supplied the bad result.

### The link opens a Jira board, work item, or 404 page

- Compare the actual hyperlink target with the canonical URL returned by the Zephyr retrieval action.
- If the response or interface constructed a URL from a plain case key, this is an agent response-rendering or instruction-compliance defect.
- If the Zephyr action itself returned an incorrect canonical URL, the integration or Zephyr-side mapping must be fixed. Editing the prompt alone will not make the URL trustworthy.

### The link opens an older or unrelated case

- Compare the stable ID and key from the create response with the record retrieved during verification.
- Check the case name, folder, creator, creation time, and correlation evidence.
- If the agent retrieved a generic "latest" or cached case instead of the stable ID from the current create call, this is an agent workflow defect.
- If the tool returned stale or mismatched data for the correct stable ID, this is an integration or source-system defect.

### The link works for one tester but not another

- Compare their Jira and Zephyr permissions.
- Treat a permission error separately from a missing record. The agent operates with the current user's access.

### The case cannot be found anywhere

- Check whether the create action succeeded, timed out, or returned an unknown outcome.
- Confirm that a read-after-write retrieval occurred.
- The correct status is CREATION_UNVERIFIED or FAILED unless the target system proves creation.

If the integration cannot return a stable ID, canonical URL, correlation evidence, and reliable read-after-write result, pause production use. Those are tool or integration controls and cannot be made dependable through a longer agent description.

## 9. What to capture in a defect report

Record:

- Date, time, and timezone
- Tester role and relevant permission level
- Exact prompt
- Jira story key and intended Zephyr folder
- Agent response and item status
- Displayed case key
- Actual hyperlink destination
- Whether the case exists in Zephyr
- Actual case name, folder, creator, and creation time
- Rovo request ID or debug reference, when available
- Selected agent or subagent and the order of actions called
- Create, retrieve, duplicate-search, and link outcomes
- Screenshots of the response and destination page
- Expected result and actual result

Do not include passwords, tokens, or other credentials.

## 10. Release acceptance targets

- Invented IDs or URLs: 0
- Broken canonical links: 0
- Duplicate creations in the regression suite: 0
- Hidden partial failures: 0
- Successful writes with read-after-write verification: 100%
- Required traceability links verified: 100%
- Expected-status accuracy across the evaluation dataset: at least 95%

Do not promote the agent if data integrity cannot be trusted, a write can be reported as successful without retrieval, or a key can be linked to a guessed URL.
